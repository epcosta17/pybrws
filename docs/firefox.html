Cloning a Firefox ClientHello, byte for byte

Part one: what a server knows about you before HTTP exists, and what it takes to reproduce it from packet captures.

Ernesto Pérez Costa · October 2026 · ~10 min

This started with something stupid. Same URL, two Python clients, same headers. One gets the page, one gets a 403. I diffed the requests field by field, lower-cased names, order included. Identical.

Which meant the server was not reacting to anything in my request. It had decided earlier. So I stopped looking at HTTP and opened Wireshark, and every number below comes out of what I found in there.

The first packet is 1,901 bytes and has no HTTP in it

Filter tls.handshake.type == 1, load a page in Firefox 157, and there it is. No URL, no User-Agent, nothing you can set from Python. What is in there is a list of cipher suites the browser supports, a list of extensions in a particular order, and some crypto key material: 

total                       1,901 bytes
  fixed header                 76
  15 cipher suites, in order
  17 extensions, in order     232   (all of them except the two below)
    key_share               1,327   70% of the whole message
    encrypted_client_hello    282

All of that is stable per browser build, so a server can hash it into a short string and look it up. These have names — JA3, JA4 — and they work about how you would expect. Measured against tls.peet.ws: 

Firefox 157   t13d1517h2_8daaf6152771_3cbfd9057e0d
httpx         t13d1712h1_ab0a1bf427ad_8e6e362c5eac
              │   │ │ │
              │   │ │ └ first and last char of the first ALPN entry
              │   │ └ extension count   (17 vs 12)
              │   └ cipher count       (15 vs 17)
              └ TLS 1.3, SNI present

They agree on the protocol version and nothing else. No header changes any of it, which is why sending perfect browser headers over a Python handshake fools nobody.

A detail worth knowing

JA4 sorts the cipher and extension lists before hashing them, and strips GREASE. That is deliberate: JA3 hashed them in wire order, so when Chrome started shuffling its extensions per connection in 2023, every Chrome produced a different JA3 and the fingerprint became useless for it. Sorting fixed that. If you want the order back there are the ja4_o and ja4_ro variants.

Five captures: what moves and what doesn't

Before you can clone something you have to know which parts of it are allowed to differ. Five consecutive captures under the same conditions, all 1,901 bytes:

FieldBehaviour across five captures
extension orderidentical — Firefox does not shuffle on TCP
cipher listidentical
randomvaries, 32 bytes
session_idvaries, 32 bytes
key_sharepayload varies, length stable at 1,327
encrypted_client_hellopayload varies, length stable at 282
every other payloadconstant

A fixed extension order is good news: it makes byte-identity a well-defined goal rather than a distribution to match. (Chrome is the opposite case, and it gets its own post.)

The 1,327 bytes you cannot copy

key_share is the client's half of a Diffie-Hellman exchange, sent speculatively in the first message so the handshake can finish in one round trip instead of two. Firefox sends three of them:

GroupBytes
0x11EC X25519MLKEM7681,216
0x001D X2551932
0x0017 secp256r165

It advertises five groups and sends shares for three. That asymmetry is itself part of the fingerprint, and it is not an oversight: the server may answer with a HelloRetryRequest asking for any group you advertised, so you have to be able to produce a share for all five.

The 1,216 are 1184 + 32: an ML-KEM-768 encapsulation key first, an X25519 public key second. That order is from the hybrid draft and I confirmed it against the capture. Both keypairs are generated per connection: 

self._x25519[group] = x25519.X25519PrivateKey.generate()
self._mlkem[group]  = mlkem.MLKEM768PrivateKey.generate()

# the share is just the two public halves, in that order
return (self._mlkem[group].public_key().public_bytes_raw()
        + self._x25519[group].public_key().public_bytes(*_RAW))

Hybrid means an attacker has to break both: X25519 today, ML-KEM when a quantum computer exists. It is aimed at "harvest now, decrypt later".

And it is the reason a captured hello cannot simply be replayed. The server's reply is computed against your public key. Paste someone else's and you do not hold the private half, decapsulation returns garbage, and the handshake dies at the Finished check with no useful error. The clone has to be structural — same shape, same order, same sizes — with live crypto inside.

Firefox sends no GREASE, except where it does

GREASE (RFC 8701) is deliberate garbage: reserved values like 0x0A0A that clients sprinkle through their cipher and extension lists so that any peer which chokes on an unknown value is found out now, rather than on the day a real new extension ships. Chrome invented it and uses it heavily.

Firefox puts none in its cipher list and none in its extension list. But it greases its encrypted_client_hello, and decoding that across the five captures gives:

FieldAcross five captures
type0 (outer), constant
kdf_idHKDF-SHA256, constant
aead_idvaries: AES-128-GCM or ChaCha20-Poly1305
config_idvaries: 0x2a, 0x87, 0x94, 0xc4, 0x6f
enc32 bytes, constant length
payload240 bytes, constant length

Encrypted Client Hello exists because the SNI — the one field that says which site you are visiting — is the last thing in TLS still sent in the clear. ECH encrypts an inner hello carrying the real name against a key the server publishes in DNS.

But if only ECH users sent the extension, the extension itself would be the signal. So browsers send a decoy of the right shape whether or not they are doing real ECH. Firefox does this by default, and this is that decoy.

Why this matters for an imitation

Hardcoding one aead_id and one config_id produces a client that is correct on any single connection and distinguishable over many, because a real Firefox varies both. Same failure mode as emitting a fixed GREASE value. "Correct once" and "correct repeatedly" are different targets, and only the second one is the job.

One assumption I checked rather than assumed: a real ECH payload would contain the inner hello, which contains the real server name, so a longer hostname could in principle lengthen it. Measured against a 66-character name, the hello grew by exactly the 43 bytes the name added and the ECH payload stayed at 240. The constant holds for any host.

The method, which is the only part that transfers

  1. Capture. A local TLS server with a self-signed cert. Open it in Firefox, accept the warning, save the raw first packet as hex. No proxy in the middle to rewrite anything — see below for why that matters more than it sounds.
  2. Parse. Walk the message field by field. Every length is written in the bytes before the thing it measures, so there is nothing to infer: you either decode all 1,901 or you have a bug.
  3. Rebuild. A profile of measured values — 15 suites in order, 17 extensions in order, every payload verbatim. No constant that did not come off the wire.
  4. Diff. Our bytes against the captured bytes, with the four genuinely-varying fields excluded by name. Everything else has to match exactly, and a test holds it there.

Step 4 is the whole method. Steps 1 to 3 can be done from a blog post and feel finished while being wrong. The diff is what tells you, and in this project it caught every mistake worth catching.

The afternoon my own browser was lying to me

Partway through, a fresh look at tls.peet.ws from Firefox reported a fingerprint matching neither my stored reference nor my client: 

stored reference  t13d1517h2_8daaf6152771_3cbfd9057e0d
this client now   t13d1517h2_8daaf6152771_3cbfd9057e0d
the browser now   t13d2713h2_bd9791dd9fd6_ecd0401ec68b

That is not Firefox's stack. Twenty-seven ciphers instead of fifteen, every one listed twice, which NSS never does. encrypt_then_mac present, which is an OpenSSL extension. renegotiation_info ahead of server_name, the reverse of Firefox's order. And none of the five extensions I had been using since the first capture to tell NSS from BoringSSL. The HTTP/2 layer was rebuilt too: stream id 1 rather than 3, no priority flag on the HEADERS frame, different window sizes.

Something was terminating both layers and re-originating them. It was NordVPN's Threat Protection, which installs a local proxy and a root certificate to inspect HTTPS — and runs while the VPN is not connected to anything. Having the app open was enough.

Worth sitting with. This is ordinary consumer software sold as a security feature, and its effect is identical to a malicious proxy: a third party replaces the TLS and HTTP fingerprints of every request you make, and nothing anywhere reports a problem. Nothing broke. No error appeared. Every page rendered normally.

The only reason it surfaced is that something in this project reports back what the server actually received. If you are capturing reference fingerprints on a machine running one of these, you are not measuring your browser. And most people have no idea theirs does this.
