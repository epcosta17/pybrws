One browser, two fingerprinting rules

Part three: Firefox keeps a fixed TLS extension order over TCP and shuffles it over QUIC. Same browser, same version, two different stacks underneath.

Ernesto Pérez Costa · October 2026 · ~9 min

Part one rested on a convenient fact: Firefox sends its seventeen TLS extensions in the same order on every connection, which makes byte-identity a well-defined goal. I had that written down as a property of Firefox.

It is a property of Firefox over TCP. Over QUIC the same browser draws a new order every connection, like Chrome. Here is how that turned up and what else came with it.

Anyone can read a QUIC handshake

QUIC does not run over TLS. It carries TLS inside, in CRYPTO frames inside Initial packets. Those packets are encrypted — with keys derived from a salt published in RFC 9001, because their purpose is integrity and version negotiation, not secrecy.

So reading a stranger's QUIC ClientHello off the wire is not an attack, it is the intended behaviour, and it takes about an afternoon:

  1. Derive the initial secrets from the published salt and the connection's destination id.
  2. Remove header protection — the packet number is masked with a sample of the ciphertext, which is a small chicken-and-egg you unwind in a fixed order.
  3. Decrypt the payload, parse the frames, reassemble the CRYPTO stream by offset.
  4. Out comes an ordinary ClientHello.

The decoder needs nothing but a crypto primitives library — there is a test asserting it imports with the QUIC library hidden — which matters, because a measuring instrument that depends on an implementation inherits that implementation's opinions.

The finding

First real capture: 231 UDP datagrams, 12 long-header connections, seven ClientHellos recovered. Six of them carry an identical set of fifteen extensions: 

0  5  10  13  16  23  27  28  34  43  45  51  57  65037  65281

…and a different order every time. Six connections, six orders, no repeats. Two never move: quic_transport_parameters then encrypted_client_hello, in that order, pinned at the end in all six.

One of the six is incoming.telemetry.mozilla.org, which nothing but Firefox contacts, and the other five share its exact transport parameter sequence. So this is one client, and that client shuffles.

Which is the opposite of its behaviour on TCP. Firefox's QUIC stack is neqo, written in Rust; its TLS-over-TCP stack is NSS, written in C. Two implementations in one browser, two fingerprinting rules, and no reason they should agree.

The practical consequence

The fixture captured an hour earlier was one sample of a distribution, not a reference, and no test may assert its order. What a test can assert is the relationship between samples: same set every time, different order every time, exactly two pinned at the end. That is what the test holds now.

Three more things QUIC changes

Three cipher suites instead of fifteen. 0x1301 0x1303 0x1302, the TLS 1.3 suites only, because QUIC forbids TLS 1.2 outright. This is the cheapest QUIC tell there is: a client offering the TLS 1.2 suites over QUIC has not thought about it for one second, and it costs a server nothing to notice.

Three extensions disappear. ec_point_formats, session_ticket and signed_certificate_timestamp. The first two follow from TLS 1.2 being unavailable. The third does not obviously follow from anything, and I have it written down as an observation rather than an explanation.

The transport parameters are not sorted. reset_stream_at (0x1d) and a GREASE id come before max_datagram_frame_size (0x20). The QUIC library I was using as an oracle sorts them. Firefox does not. Which is a whole second fingerprint surface that only exists on this transport: which parameters, in what order, with what values.

Three things I got wrong, which is the useful part

1. The capture was two browsers

The seventh connection, to www.bing.com, is not Firefox. Eleven extensions instead of fifteen, and missing every NSS marker the others have — renegotiation_info, delegated_credentials, status_request, extended_master_secret, record_size_limit. Its transport parameters are google_connection_options, initial_rtt, google_version. Chromium-shaped.

My first reading had all seven as one client, so the report said "7 distinct orders across 7 connections" and I nearly wrote down that the extension set varies too. It does not. The sets split cleanly into two clients. A capture of UDP 443 holds whatever the machine was doing, which is obvious once stated and was not obvious while reading the output.

The tool now groups by extension set before saying anything about order, so a second client shows up as a second client instead of as noise inside the first one's measurement.

2. Then I made the same mistake again, one report later

I wrote that Firefox draws its GREASE transport parameter per connection, "with an eight-byte one observed". It does not. 0xff02de1a appears in all six Firefox connections; the eight-byte one belongs to the other client. I had mixed the two together again, in exactly the way I had just finished fixing the tool to prevent.

And the constant is more interesting than the variation would have been. A value that never changes is not greasing anything, and this one carries the varint 1000, which is a plausible min_ack_delay. The registered codepoint for that is 0xff04de1b, one of a family of 0xff0?de1? draft codepoints — so this is most likely an old draft of it that satisfies the reserved 31N+27 pattern by coincidence. The tool still labels it GREASE because the formula says so, and labels it as unidentified, because it is.

3. The elegant hypothesis was wrong

One host, cloudflare-ech.com, has Firefox's exact extension set and Firefox's pinned tail but sends three transport parameters where the other five send fourteen — no flow control credit at all, which is not a functioning set.

I had a tidy explanation ready: the host publishes a real ECH config, so what I captured is the outer decoy hello with the working parameters encrypted inside. It would have been the first real-ECH hello in the project.

Its ECH extension is 282 bytes. The same greased length as every other connection in the capture. No real ECH anywhere.

The guess was plausible and fitted the evidence I had and was simply wrong, which is the argument for printing the column rather than reasoning about what it would contain. What held instead was arithmetic: three parameters measure about 26 bytes on the wire against 86 for fourteen, a difference of 60 — and two hosts with server names of equal length produced hellos of 1,900 and 1,840 bytes. Sixty, predicted from the parameter count alone, confirmed by a measurement that does not depend on the decoder that produced the count.

What Firefox is doing differently with that one host is still unknown. It is one connection in six and nothing rests on it.

And one from the writing desk

I wrote the transport parameter table from memory and it was wrong where it mattered: 0x1d is reset_stream_at, not unknown, and min_ack_delay is 0xff04de1b, not what I had. The IANA registry settled it in one fetch. The only reason I checked at all is that the arithmetic on the GREASE pattern was cheap enough to do, and it disagreed with me.

Why any of this matters

If you are building an imitation, the headline is that a browser is not one fingerprint. It is one fingerprint per transport, and the transports do not share code, so they do not share habits. Test your HTTP/3 path separately or you are shipping a client whose two halves describe different programs.

If you are on the detection side, the inverse: QUIC hands you a second independent signal for free, legible without a key, and quic_transport_parameters is a surface most imitation tools have not got to yet. The TLS 1.2 cipher suite check alone catches anything careless.

And for everyone: the most productive hour of this whole project was the one where a tool printed a column I had not thought to ask for. Every mistake above was caught by data that was already there and not being shown. Print the column.
