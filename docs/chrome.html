Chrome shuffles, and a question I could not answer

Part two: what adding a second browser does to code that worked perfectly for the first, and a day spent eliminating hypotheses for a question I had invented.

Ernesto Pérez Costa · October 2026 · ~9 min

Part one ended with a Firefox ClientHello reproduced byte for byte. The profile that produced it was a flat list: fifteen cipher suites, seventeen extensions, each payload a literal captured off the wire. Emitting it was a loop.

Then I added Chrome, and almost none of that survived.

There is no "Chrome's extension order"

Firefox sends the same extension order on every connection. Chrome draws a new one each time. Capture it six times and you get six orders, which means the target is not a sequence to copy but a distribution to reproduce.

Not quite uniformly, though. Chrome pins one extension at each end of the list, and both of them are GREASE.

GREASE

Generate Random Extensions And Sustain Extensibility, RFC 8701. Sixteen reserved values following the pattern 0x0A0A, 0x1A1A … 0xFAFA, which clients send on purpose in their cipher lists, extension lists, supported groups and ALPN.

It is a vaccine against ossification. If some middlebox hardcodes "I know every valid extension" and breaks on an unknown one, you want to find that out continuously, not on the day you ship a real new extension. Chrome invented it for exactly that reason, and it has to be stripped before computing JA3 or JA4 or the fingerprint would change every connection.

So Chrome's hello is: a GREASE extension, eighteen real ones in a drawn order, another GREASE extension. Twenty in total. Reproducing that needs a per-connection draw, not a list.

The one-in-sixteen bug

The first version drew each pinned GREASE value independently. Which is fine fifteen times out of sixteen, and on the sixteenth both draws return the same value — and now the hello has two extensions of the same type.

That is an outright RFC 8446 violation ("there MUST NOT be more than one extension of the same type"), and it has a second tell that is worse, because it is quiet: a hello one byte shorter than any real capture. A conforming server may reject it. A fingerprinting service will just record it.

The fix is to draw the second value from the fifteen that are not the first. My first attempt at that was a redraw loop, which hung forever the moment a test pinned the random number generator to a fixed value. Bounded rejection sampling, 64 attempts, then fail loudly.

What this did to the design

Firefox's profile holds EXTENSIONS, a list. Chrome's needs extension_order(ctx), a function. So the field had to become "either a list or a callable", the cipher suites too, and several payload builders with it.

The abstraction was not correct until a second browser existed to break it. One sample is not a design input — it is an example you have mistaken for a design input, and you only find out when the second one arrives.

Nothing above TLS matches either

I assumed the HTTP/2 layer would be free. It is the same protocol; how different can two implementations be? Captured side by side:

Not one field matches, and they do not even send the same settings: Firefox sends number 5 where Chrome sends number 6. There is a fingerprint built from exactly this — Akamai's — and it is as distinctive as the TLS one.

Verified against a real Chrome, field by field

A real Chrome 155 against the same service, compared value by value rather than by eye: 

ja4                  identical
ja4_r                identical
peetprint_hash       identical
akamai_fingerprint   identical
session id length    identical
HTTP/2 header order  identical
HEADERS priority     identical   weight 256, exclusive, depends_on 0

ja4_r is the informative one: the raw sorted form with every cipher, extension and signature algorithm spelled out rather than hashed. It matches. So does the trust_anchors payload, 186 bytes byte for byte, and the greased ECH length, 144, which is one of the three sizes this profile draws from.

A thing I did and then undid

That 186-byte trust_anchors payload: I first wrote it from my own idea of what the structure should contain. It was invented. Not wrong-in-a-detail — fabricated, 186 bytes of plausible-looking structure that no browser ever sent.

It was replaced with the bytes extracted from the capture, and a test now asserts the two are equal. If a value is in the profile and it did not come off the wire, it is decoration.

And then yelp

With every measurable fingerprint matching a real Chrome, one target still refused: yelp.com served the Firefox profile 5 times out of 5 and refused the Chrome profile 5 out of 5. Same machine, same proxy, same headers logic, interleaved rounds.

That is a strong signal, so I went looking for the tell. In order:

HypothesisResult
Cache-Control: max-age=0, an artefact of capturing on reloadsremoved it; no change either way
The 2×2 crossing of TLS layer against HTTP layerconfounded by construction; it could not have answered
The HTTP/2 frame sequencereal Chrome sends exactly our three frames
The locale (we send en-US, the capture had en-MX)sent the captured locale; 0 of 3 either way
The drawn extension orderreplayed three real captured orders verbatim; 0 of 2 each
A defect in the profileevery fingerprint matches a real Chrome 155

The shuffle was the best remaining idea, and it is a good one: ja4_r and peetprint both sort the extension list, so the wire order is the one property of the hello that none of the matching hashes capture. If anything was going to be the invisible difference, that was it. Replaying real captured orders killed it.

I also checked whether the draw itself looked wrong, by recording the position each of the eighteen shuffled extensions took across six captures: 

psk_key_exchange_modes   [10, 6, 5, 10, 5, 6]     span 5-10
server_name              [ 8, 10, 15, 8, 12, 11]  span 8-15
signature_algorithms     [17, 0, 17, 11, 13, 17]  span 0-17

Every span is wide and the narrowest covers six positions. The draw looks uniform. Six samples cannot prove that it is — but there is no evidence against it, and inventing structure to fit a theory is the thing a notebook exists to prevent.

The answer was in a sentence I had already been given

Before all of that, I had asked whether the page loaded in a real Chrome on the same machine. The answer came back: "the page comes up in Chrome, it verifies and loads."

I read that as no challenge, and spent the rest of the day on the difference between a browser that sails through and clients that do not.

"It verifies." If a verification screen appears before the page, then a real Chrome is challenged too and gets through by running the JavaScript. Every observation then fits, with nothing left to explain: 

real Chrome          challenged, solves it, loads
our Chrome           challenged, cannot solve it, 403
curl_cffi Chromium   challenged, cannot solve it, 403
our Firefox          not challenged, 200

There is no tell. The profile is correct. yelp challenges Chromium-shaped clients and serves Firefox-shaped ones, and a JavaScript challenge is a boundary no fingerprint crosses — a real browser passes it by executing the script, which is a different capability, not a better disguise.

I have not independently watched that verification screen appear, so I am calling this the explanation that fits rather than the confirmed one.

The lesson, which is not technical

Six hypotheses, each properly tested and properly eliminated, all downstream of misreading one word in a one-line report from the person holding the browser.

The eliminations were not wasted — the profile is now verified against a real Chrome field by field, which it was not before. But the question they answered was one I invented. Measuring carefully in the wrong direction is still the wrong direction, and the cheap guard against it was one clarifying question I did not ask.
