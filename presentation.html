02

Why that makes it a fingerprint

Every field above is the same on every connection a given browser build makes. So a server can hash the whole thing into one short string and look it up. That is all JA3 and JA4 are.

Firefox 157 t13d1517h2_8daaf6152771_3cbfd9057e0d
httpx (Python) t13d1712h1_ab0a1bf427ad_8e6e362c5eac

t13d = TLS 1.3 with SNI  ·  then cipher count, extension count, first ALPN  ·  then hashes of the cipher and extension lists — sorted, GREASE stripped

They agree on the version and nothing else. Firefox offers 15 ciphers and 17 extensions, httpx offers 17 and 12, they lead with a different ALPN entry, and both hashes differ. No header changes any of it, so perfect browser headers sent over this handshake fool nobody.

And you can't fix it from outside

Python's ssl hands you OpenSSL's hello. OpenSSL has no option for "send these 17 extensions in this order" — it isn't trying to be Firefox. The only way through is to write the message yourself.

03

How we cloned Firefox's

Four steps, and the last one is the only one that proves anything.

01  CAPTURE

Make Firefox talk to us

A local TLS server with a self-signed cert at :4443. Open it in Firefox, accept the warning, and save the raw first packet to a hex fixture. No proxy in the middle to rewrite anything.

02  PARSE

Read the bytes, don't guess

Walk the message field by field. Every length is written in the bytes before the thing it measures, so there is nothing to infer — you either decode all 1,901 or you have a bug.

03  REBUILD

A profile of measured values

15 suites in Firefox's order, 17 extensions in Firefox's order, every payload copied verbatim from the capture. No constant in the profile that didn't come off the wire.

04  DIFF

Compare until it's zero

Our bytes against the captured bytes. Four fields are allowed to differ because they must change per connection. Everything else has to match exactly, and a test holds it there.

Step 4 is the whole method. Steps 1–3 can be done from a blog post and feel finished while being wrong — the diff is what tells you, and it caught every mistake worth catching.

The 1,327 bytes you cannot copy

key_share is not a value to paste. It is a real post-quantum keypair, generated per connection. The server answers with its own half and both sides do the maths; paste a captured one and nothing decrypts.

So the clone has to be structural: identical shape, identical order, identical sizes — with live crypto inside.

That's the ClientHello done. It is one message of many, and everything after it — the rest of the handshake, HTTP/2, HTTP/3 — has a fingerprint of its own.

05

So that's what pybrws is

An HTTP client where the fingerprint is a parameter instead of a side effect of whichever TLS library you happened to import.

from pybrws.client import get
r = get("https://example.com", profile="chrome155")
TLS

1.2 and 1.3

Handshake, record layer, key schedule, resumption, client certificates. Written here, not configured.

TRANSPORT

HTTP/1.1, /2, /3

Each one sends its profile's own settings, frame order, window sizes and header order.

PLUMBING

The boring half

Cookies, sessions, connection pool, proxies, redirects, streaming, content decoding.

PROFILES

Three, so far

Firefox 157 over TCP, Firefox 157 over QUIC, Chrome 155 — each measured separately.

Built on two libraries and nothing else. cryptography for the primitives — AES, X25519, ML-KEM — and aioquic for QUIC's transport. Every byte whose shape is a fingerprint is ours.

It does not run JavaScript. So a "checking your browser" page is out of reach by design, not by accident. The fingerprint decides one layer earlier: whether you are sent there at all.

The test for whether it worked

It wasn't right the first time
