# Handoff

`README.md` is the user guide and `NOTEBOOK.md` is the full lab record in
date order. This file is the one-page orientation -- what works, what the
known gaps are, and which decisions are load-bearing. Start here before
changing anything.

## What it is

An HTTPS client written from scratch in Python whose TLS and HTTP fingerprint
is byte-identical to Firefox 157 on Windows. It exists to find out what makes
a request look automated, by building the thing and measuring it.

Working: ClientHello, TLS 1.3 handshake including `X25519MLKEM768`, HTTP/2,
HTTP/1.1, HelloRetryRequest, certificate verification, session
resumption, HTTP/2 multiplexing, a concurrent fetcher, cookies, sessions with connection reuse,
outbound HTTP CONNECT and SOCKS5 proxies, a CLI, a MITM proxy that lends the
fingerprint to other languages, request bodies and header merging.

    .venv/bin/python -m unittest discover -s tests -t . -v   # 619, 3 skipped
    .venv/bin/python tools/verify.py                         # 18 live checks
    .venv/bin/python tools/ab_test.py                        # targets over time

## The two rules this project runs on

**Clean room.** The problem was reconstructed without reading
`curl-impersonate`, `uTLS`, `curl_cffi`, `tls-client` or `camoufox`. That
rule has served its purpose; opening them now is the intended last step, and
the comparison is worth writing up. Do not quietly fold their code in and
leave the README claiming otherwise.

**Nothing goes in the profile that was not measured.** Every constant comes
from a capture stored in `fixtures/reference-*`, and a test asserts the
generated bytes equal the capture. Where something is inferred or unknown the
code says so in a comment. Four readings were retracted during development
because they did not replicate; see `NOTEBOOK.md`. If you add a constant,
capture it with `tools/catch_hello.py` or `tools/catch_request.py` first.

## How to measure, having got it wrong four times

- **Always run the baseline arm.** `httpx` beside this client. A target that
  serves both proves nothing about the fingerprint. g2 with a query string
  looked like a win until httpx passed it too.
- **Interleave the arms** across rounds, so drift hits every cell.
- **Keep a control** that serves everyone, or a column of passes is unreadable.
- **Three samples is not a result.** A header contrast on glassdoor was 3/3
  against 0/3 and dissolved completely over five more rounds.
- **The address is half the outcome.** The same client passes from a domestic
  line and fails through a commercial ISP proxy. `tools/isolate.py` crosses
  the two; `tools/ab_test.py` changes both at once and says so.
- **Distinguish 429 from 403.** Rate limiting is earned by measuring, not a
  verdict on the client.

## What is measured, what is not

Measured, with a fixture and a byte-identity test: the ClientHello, the
HTTP/2 SETTINGS, WINDOW_UPDATE, stream id, HEADERS flags and priority, the
header order and values for a navigation, for a navigation carrying cookies,
for an image subresource, for a `fetch` POST, and for a form POST both
submitted by script and submitted by a click.

The HTTP/2 sets are measured too, with `tools/catch_h2.py`, which speaks
enough HTTP/2 to decode a browser's HEADERS frame. Nothing in the profile is
inferred any more.

Unmeasured, and marked: the pattern of later WINDOW_UPDATE frames, which
Firefox batches and this client does not; and where a browser puts the cookie
extension in the ClientHello after a HelloRetryRequest.

**The resumed ClientHello** is measured, in
`fixtures/reference-firefox-157-windows-{fresh,resumed}.hex`, both from one
run of `tools/catch_resumed.py`. Both come back clean through the differ, and
`tests/test_resumed.py` holds them.

It was worth taking. Firefox does not append `pre_shared_key`, it swaps
`session_ticket` for it, so the extension count stays at seventeen. We were
appending, which put us at eighteen -- `t13d1518h2` against the browser's
`t13d1517h2`, a difference a server reads by counting rather than hashing.

One number in it is fitted rather than measured, and is marked in the profile
and in a test: the greased ECH payload grows when a PSK is offered, by the
pre_shared_key extension's wire size plus one. The payload stands in for an
encrypted inner ClientHello which now carries a PSK itself, so the growth is
expected; the leftover byte is not explained. A single capture cannot
separate a constant from padding rounding up.

The longer-hostname capture has since been taken, with a 66-character name
against the original 23, and it settled the half of this that mattered most.
The ECH payload stayed at 240 bytes in the fresh hello and the whole hello
grew by exactly the 43 bytes the name added. So `ECH_PAYLOAD_SIZE` does not
track the server name, and the constant measured at one name is right for
every host -- which was the real risk here, since a name-dependent payload
would have made our fresh hello wrong on every fetch, not just on resumption.

That capture also reported the same residual of 1 against a hello 43 bytes
longer, which rules out padding keyed to the hello's size. What is still
untested is a *different pre_shared_key size*, which needs a ticket of
another length. Two levers failed: `--alpn h2` changes the ticket but the
tool only speaks HTTP/1.1, so the browser never reloads, and
`SSLContext.set_ciphers` cannot pin a TLS 1.3 suite, which OpenSSL keeps
behind `SSL_CTX_set_ciphersuites`. Teaching `catch_resumed.py` enough HTTP/2
to answer would unlock the first.

Note that the existing capture resumed under `TLS_AES_256_GCM_SHA384`, so its
binder is 48 bytes and its pre_shared_key extension is sixteen longer than a
SHA256 one. That is the server's doing, not the browser's. The test derives
the suite from the binder length rather than naming it.

    python tools/catch_resumed.py --fresh fixtures/one.hex --resumed fixtures/two.hex

## Known gaps, roughly by value

1. **Chrome 155 is measured, and it changed the design.** The ClientHello
   comes from six captures in one run of `catch_hello.py --count 6`; the
   HTTP/2 and HTTP/1.1 sides from `catch_h2.py` and `catch_request.py`.
   `tests/test_chrome_profile.py` holds all of it, 53 tests.

   What it says. The extension order is **drawn** per connection -- six
   captures, six orders, one set -- with a greased extension pinned at each
   end. Chrome greases six lists, always at the head: cipher suites,
   signature_algorithms, supported_groups, supported_versions, key_share, and
   both ends of the extension list. Five are independent draws;
   supported_groups and key_share share one, which the protocol requires.
   Three codepoints are unassigned in IANA and named here from their shape:
   application_settings at 0x44cd, a constant 186-byte list of five-byte
   identifiers at 0xca34, and two constant bytes at 0x12e0.

   Its HTTP/2 fingerprint matches Firefox's in **no field at all**, down to
   which settings are sent: Chrome sends 6 (max header list size) and Firefox
   sends 5 (max frame size). Verified by pointing our own client at
   `catch_h2.py` -- the recorded frames are byte-identical to Chrome's, and
   the header order including pseudo-headers matches field for field.

   What writing it found. Three defects, each caught by comparing against a
   capture rather than against what had been typed: the trust-anchors payload
   had been **invented** rather than extracted and is now the captured bytes;
   `renegotiation_info` was missing from the shuffled set, giving nineteen
   extensions where the browser sends twenty; and the two greased extension
   types could collide one time in sixteen, which RFC 8446 forbids and which
   produced a hello one byte shorter than any capture. A length no browser
   produces is the cheapest possible tell.

   Seven more captures closed most of the rest. Measured now: a form POST by
   script and by click -- the click adds exactly `Sec-Fetch-User` and changes
   nothing else, which is the only way to learn whether that header depends
   on a real user activation; an image subresource over HTTP/2, where four
   Sec-Fetch values and Accept differ from a navigation and `priority` is a
   bare `i`; and where a cookie goes, which is before `priority` over HTTP/2
   and last over HTTP/1.1, so `H1_COOKIE_BEFORE` is None and
   `headers.insert_before` now reads that as the end on purpose rather than
   by accident.

   The HTTP/2 POST set was derived and is now measured, and **the capture
   refuted the derivation**: the real set carries `priority: u=1, i`, which
   the HTTP/1.1 POST has no equivalent of, and a derivation cannot know where
   a cookie goes. That is the argument for labelling a derivation as one.

   The form POSTs over HTTP/2 are measured too, and the click adds exactly
   `sec-fetch-user` there as well, with `priority: u=0, i` -- a navigation
   priority, against the `u=1, i` a fetch POST carries.

   **One measurement is missing: an image subresource over HTTP/1.1.** The
   capture was attempted and `--any-request` returned the document again,
   byte-identical to the navigation capture, so there was nothing to record.
   A test asserts the two files are identical rather than letting one look
   like a measurement, and `H1_IMAGE_HEADERS` stays in `UNMEASURED`. Asking
   for it raises `client.Unmeasured`, which names it and the tool.
   Resumption, HelloRetryRequest and QUIC are also unmeasured for Chrome.

   Taking those captures exposed something older: **nothing in the library
   routed to the image header sets.** They had been measured constants in the
   Firefox profile since early on and were unreachable, so every image a
   scraper fetched went out with navigation headers -- a request claiming to
   be a document while asking for a PNG, which differs in Accept, all three
   Sec-Fetch values and Priority. `header_set` now takes `kind="image"`.

   Also machine-specific and flagged: `ACCEPT_LANGUAGE` carries the locale of
   the machine it was captured on, `en-MX,en-GB;q=0.9,...`, which is a
   fingerprint of a person rather than of a browser.

2. **TLS 1.2 and client certificates are done**, and both were found by a
   sweep rather than planned. `pybrws/tls12.py` carries the PRF, the key
   block, the two AEAD record constructions and both Finished messages;
   `handshake.py` branches on the ServerHello. ECDHE with AES-GCM and
   ChaCha20-Poly1305 is implemented, the CBC and static-RSA suites are
   refused by name, and `extended_master_secret` is there because Firefox
   asks for it.

   Tested against Python's `ssl` as a TLS 1.2 server, which makes OpenSSL the
   oracle for every derivation at once: swapping the two randoms in the key
   block, changing the verify_data length, using one Finished label for both
   directions, or skipping the extended master secret each fail all seven
   integration tests.

   It also uncovered a bug that had been invisible since the beginning. The
   compatibility ChangeCipherSpec was going out immediately after the
   ClientHello instead of before the second flight, which RFC 8446 appendix
   D.4 is explicit about. Every TLS 1.3 server tolerated it; a TLS 1.2 server
   answers `handshake_failure`, since a ChangeCipherSpec before the
   ClientKeyExchange is a protocol violation there. The bug could not be seen
   for as long as 1.2 was unreachable, and 1.2 could not be reached because
   of the bug.

   Still unimplemented and marked: the CBC suites, the static-RSA suites, and
   TLS 1.2 session resumption through `session_ticket`. Also
   `iberia.com`, `swisscom.ch` and `aena.es` fail certificate chain
   validation, which is unrelated and not looked into.

3. **A certificate chain question.** Three hosts fail validation and it is
   not known whether their chains are odd or our intermediate handling is.

4. **HTTP/3.** Reading and writing both work. The reading side: `pybrws/quic.py`
   recovers a ClientHello from Initial packets, which need no secret --
   RFC 9001 publishes the salt and the header carries the connection ID --
   and `tools/read_quic.py` gets them out of a pcap or pcapng.

   The Firefox capture has been taken. What it says:

   - **Fifteen extensions**, always the same set:
     `0 5 10 13 16 23 27 28 34 43 45 51 57 65037 65281`. Against TCP's
     seventeen, `ec_point_formats`, `session_ticket` and
     `signed_certificate_timestamp` are gone and `quic_transport_parameters`
     is new.
   - **The order is shuffled per connection.** Six connections, six distinct
     orders, identical sets. Exactly two are pinned, at the end:
     `quic_transport_parameters` then `encrypted_client_hello`. This is the
     opposite of Firefox on TCP, where the order is fixed -- its QUIC stack
     is neqo, in Rust, not NSS. So a QUIC profile draws an order rather than
     storing one, and no test may assert a single order.
   - **Three cipher suites**, `0x1301 0x1303 0x1302`, against fifteen on TCP,
     since QUIC forbids TLS 1.2. The cheapest tell on the protocol.
   - **Fourteen transport parameters, not sorted.** `reset_stream_at` (0x1d)
     and `0xff02de1a` come before `max_datagram_frame_size` (0x20). aioquic
     sorts its own; Firefox does not.
   - **`0xff02de1a` is constant**, in all six connections, carrying the
     varint 1000. It satisfies the 31N+27 reserved pattern, so the tool
     labels it GREASE, but a value that never changes is not greasing and
     1000 is a plausible `min_ack_delay` -- whose registered codepoint is
     0xff04de1b, one of a family of `0xff0?de1?` draft codepoints. Treated as
     a constant to copy. Not identified.

   Measured and unexplained: `cloudflare-ech.com` has Firefox's exact set and
   pinned tail but **three** transport parameters where the other five send
   fourteen -- `max_ack_delay`, `initial_source_connection_id`,
   `version_information` and nothing else, which carries no flow control
   credit at all. It is not a decoder fault and not a real-ECH outer hello:
   its ECH extension is 282 bytes, the same greased length as every other
   connection. The byte count corroborates it independently -- three
   parameters measure about 26 bytes against 86 for fourteen, a difference of
   60, and `www.cloudflare.com` and `cloudflare-ech.com` have equal-length
   server names and hellos of 1900 and 1840 bytes. So it is real and the
   trigger is unknown. One connection in six; nothing is built on it.

   **A capture of port 443 holds more than the browser under test.** The
   first one had Chrome running alongside Firefox, and its connection to
   bing.com -- eleven extensions, a 218-byte ECH against Firefox's 282, and
   Google transport parameters -- read as the same client made Firefox's
   order look less structured than it is, and made a constant GREASE id look
   as though it varied. Both wrong readings came from the same mistake.
   `--all` groups by extension set first for that reason.

   **The write side works.** `pybrws/quic_impersonate.py` makes aioquic send
   the profile's hello: seven hosts out of seven connect over HTTP/3, six
   selecting X25519MLKEM768, and the hello matches the capture at 1931 bytes
   with every static payload identical.

   It costs five monkeypatches into aioquic's private surface, each named in
   that module's docstring and each asserted by a test, so an aioquic upgrade
   breaks a test rather than a connection:

   - `push_client_hello`, the writer. Called inside
     `with push_message(key_schedule, output_buf):`, which hashes whatever
     lands in the buffer, so replacing it keeps the transcript correct for
     free. This was the only seam planned.
   - `Context._client_send_hello`, wrapped only to reach the connection,
     since the writer is handed a buffer and a hello and nothing else.
   - **The key exchange.** aioquic has no post-quantum group and silently
     skips unknown ones, so all three key shares are ours from
     `keyexchange.py` and the shared secret is too. `decode_public_key`
     keeps the server's raw share and returns a type-compatible dummy, and
     `_x25519_private_key` becomes a stub whose `exchange` returns the real
     secret. The most fragile part, and the most load bearing.
   - **Compressed certificates.** Advertising `compress_certificate` because
     Firefox does means servers send handshake type 25, which aioquic names
     and never dispatches. RFC 8879 section 5 hashes the *compressed*
     message, so the interception hashes it itself rather than letting
     aioquic hash what came out of the decompressor.
   - **The connection ids.** aioquic uses one length for both; RFC 9000
     section 7.2 requires the initial destination id to be at least 8 bytes
     while Firefox's source id is 3. Three bytes for both is a violation
     that Cloudflare tolerated and Google answered by dropping every
     Initial packet in silence.

   aioquic is a transport dependency in the same category as `hpack`, not an
   impersonation library, so the clean-room rule has nothing to say about it.

   **The request path exists.** `pybrws/h3.py` gives `h3.get(url)`
   synchronously, running its own event loop, plus `Http3Client` for callers
   already in one. Three hosts fetched over h3 with gzip negotiated and
   decompressed.

   Its headers are **not measured**, and that is the live gap. The HTTP/2
   navigation set is used as a starting point, which `tools/h3_compare.py`
   showed matches curl_cffi's firefox147 header for header and in order --
   weak evidence, two guesses agreeing, but evidence.

   The **pseudo-header order is probably wrong**. Ours is
   `:method :path :authority :scheme`, inherited from our measured HTTP/2
   profile; curl_cffi's firefox target sends
   `:method :scheme :authority :path`. One of the two is wrong about Firefox
   over HTTP/3 and only a capture settles it. This is an inherited
   assumption of exactly the kind this project exists to catch, so it is
   named in `pybrws/h3.py`, in `tests/test_h3.py` and here.

   Measured against curl_cffi (`tools/h3_compare.py`), using our own server
   as the oracle because tls.peet.ws advertises h3 and does not serve it:
   extension sets, cipher suites, session id, key shares and request header
   order all agree. Three extensions differ and in all three we match the
   Firefox 157 capture -- `supported_groups` 12 bytes against 16,
   `quic_transport_parameters` 86 against 79, `encrypted_client_hello` 282
   against 186 -- though some of that may be 147 against 157 rather than a
   modelling difference.

   Two differences are behavioural and not version-dependent. **curl_cffi
   does not shuffle**: one extension order across four connections, where
   real Firefox gave six orders in six. And **its ECH payload length
   varies**, 186 to 250, where Firefox's is a constant 282. Both are tells
   in their own right.

   Also unmeasured: Firefox's own initial destination id length, which needs
   packet headers rather than a handshake.

   Concurrency is done, as multiplexing within a connection and a thread
   pool across them; streaming is done; what is missing is an asyncio path,
   which HTTP/3 will want since aioquic is asyncio.

## Things that cost time here

- **Fixture line endings.** The captures contain the CRLF that HTTP requires.
  `autocrlf` had normalised them in the repository, so the byte-identity
  tests passed on Windows and failed anywhere else. Pinned in
  `.gitattributes`; verify with a clean clone, not a local checkout.
- **The references are from Windows.** `tools/verify.py` checks `tcpip.p0f`
  against a Windows capture, so that one check fails on another OS while the
  other seventeen pass. Running the Windows profile on a Mac also leaves the
  TCP layer saying macOS and everything above saying Windows, which is the
  inconsistency this project is about.
- **`tls.peet.ws` fails intermittently.** It is a free service this project
  leaned on hard. A failure there is usually transient; confirm with httpx
  before debugging.
- **Writing code through a shell heredoc mangles backslash escapes.** Several
  files were corrupted that way. Write the file directly.
- **Targets flap.** glassdoor answered 200, then 403, then 200 again within
  an hour. Record a rate with a timestamp, never a verdict.

## The demo

`notebooks/demo.ipynb`, seven sections, outputs stripped. Fetches one URL with `httpx`
and with this client and renders both, sweeps four protection vendors,
shows why the baseline arm exists, compares the fingerprint the server
reported against a real Firefox, and asks whether a session changes the
outcome. Three of the seven sections are about limits and mistakes.

JupyterLab sanitises HTML in an untrusted notebook and the iframes vanish;
each result also prints a plain summary line so the point survives that.
